# 参照実装のテストと確認の結果

OLDP(Optical Lab Device Protocol)第 1.0 版の参照実装について、テストの内容、H8/3069F の基板で測った値、実装の制限、確かめていないことをまとめる。規格の本文は、規格のリポジトリ [optical-lab-device-protocol](https://github.com/NrivYuki/optical-lab-device-protocol) の `docs/spec.md` にある。

機器の側は C で書いた。動的なメモリ確保はしない。暗号の部品は、ChaCha20-Poly1305 に Monocypher 4.0.3 を使い、X25519 は 16 ビットの CPU 向けに `c/src/oldp_x25519.c` を、SHA-256 は `c/src/oldp_sha256.c` を書いた。ホストの側は JavaScript で書き、vca-hub の拡張で使う。

## テスト

このリポジトリのテスト:

| 対象 | 内容 |
|---|---|
| JavaScript | `spec/vectors` の全て、セッションのバイト列(機器の側・ホストの側)、UART の再送とやり直し、誤りの扱い、UART の使用中に暗号で確かめられないフレームを捨てること、`REQUIRE=`、接続数の上限、`spec/` が規格のリポジトリと同じであること |
| C | SHA-256(FIPS 180)、HMAC(RFC 4231)、X25519(RFC 7748 の例・1000 回の繰り返し・Monocypher との比較)、ChaCha20-Poly1305(RFC 8439)、`spec/vectors` の全て(TCP・UART のセッションのバイト列を含む)、機器の誤りの扱い、UART の使用中に暗号で確かめられないフレームを捨てること、`REQUIRE=`、線の上でフレームが失われたり壊れたりしたときの再送 |

vca-hub を通した確認([vca-hub-extension](https://github.com/NrivYuki/vca-hub-extension) のリポジトリ):

| 対象 | 内容 |
|---|---|
| vca-hub の拡張のテスト | DCS の機器と OLDP の機器の間の両方向の受け渡し、送り先への送信、加工条件の拡張との併用、AVAIL、同じ PUT の 2 度目、受けられない値、拡張の受け口、OLDPKEY |
| `tools/verify-device.js` | このリポジトリの C の模擬機器(UART・TCP)と H8 の基板(UART は 9600・19200・38400・57600 bps、LAN)を vca-hub とつなぎ、ペアリング(両側の受付と解除)・PUT・GET・RESULT・TIME・PING(両方向)・INFO・AVAIL(接続したとき・接続している間)・受けられない値・1440 点の玉型を確かめる。H8 の基板では、標準の拡張 OLDPKEY による鍵の交換と、再起動した後も新しい鍵が残ることも確かめる |

## H8/3069F で測った値

H8/3069F(20 MHz)で測った値である。UART では、PC の中継を通して vca-hub へつないだ。LAN では、10BASE-T(RTL8019AS)で PC と直結し、vca-hub へ TCP でつないだ。セッションの時間は `tools/verify-device.js` で測ったもので、PC の道具を起動する時間を含む。

| 項目 | 値 |
|---|---|
| プログラムの大きさ | 47.2 KB(暗号・TCP/IP・項目の辞書・約 2 KB の見本のジョブを含む) |
| RAM(変数) | 8.0 KB(フレームの上限 512 バイト、受信のリングバッファ 384 バイト。スタックを除く。TCP の受信には UART の作業領域を使う) |
| X25519 の 1 回の計算 | 5.7 秒 |

| セッション | UART 9600 bps | UART 19200 bps | UART 38400 bps | UART 57600 bps | LAN |
|---|---|---|---|---|---|
| PUT(片眼 360 点、約 2 KB) | 27.9 秒 | 26.5 秒 | 25.6 秒 | 25.3 秒 | 24.5 秒 |
| GET と RESULT(両眼 360 点) | 30.4 秒 | 27.7 秒 | 26.2 秒 | 25.8 秒 | 24.9 秒 |
| 1 つのセッションで TIME・PING・PUT・GET・RESULT・INFO | 33.5 秒 | 29.4 秒 | 27.3 秒 | 26.7 秒 | 25.0 秒 |
| GET と RESULT(両眼 1440 点) | 45.1 秒 | 35.8 秒 | 31.2 秒 | 29.9 秒 | 27.2 秒 |

どのセッションも、約 25 秒はハンドシェイク(機器の側の X25519 の計算)である。UART の 4 つの速度では、全てのセッションで、再送・壊れたフレーム・SCI の受信の誤り・受信のバッファのあふれが 0 回だった(基板の `log` コマンドで数えた)。

### 規格に合わない速度

規格の 4 章は、実際の速度と一覧の値との差を範囲の中に収めるよう定めている。20 MHz の H8 では 115200 bps に最も近い速度が 125000 bps(+8.5%)になり、この範囲を超える。

| PC の側の速度 | 結果 |
|---|---|
| 115200 bps | 全く通じなかった(1 文字の終わりまでにずれが 0.8 ビットほどになり、正しく読めない) |
| 125000 bps(基板と同じ) | `verify-device.js` の全ての項目が通った。ただし、3 つのセッションで受信のバッファがあふれ、再送で立ち直った |

## 制限

- H8 の基板のソフトウェアの更新では、シリアルから受けたデータを CRC-32 で確かめるだけで、署名は確かめない(検証を繰り返しやすくするための改造。[h8-board.md](h8-board.md))。
- 機器の鍵は、組み立てのときにファームウェアへ埋め込んだ 1 つの鍵から始まる(標準の拡張 OLDPKEY で替えられる)。製造の工程で機器ごとに鍵を入れる手順は持たない。
- H8 の基板の受信のリングバッファ(384 バイト)は、RAM の残りで大きさを決めたため、1 つのフレームの全部(最大で約 520 バイト)は入らない。規格の一覧の速度では足りたが、より速い線では、フレームを処理する間にあふれることがある(125000 bps で起きた)。

## 確かめていないこと

- 基板のリセットボタンによる起動(電源の入れ直しと、起動の入口へ飛ぶコマンドでは確かめた)
- PC の中継を挟まずに、機器とホストを線で直結した形
- LAN での再送(確認の間に、パケットの欠落が起きなかった)
- スイッチやルーターを挟んだ LAN(PC との直結では確かめた)
- DHCP(H8 の基板はアドレスを設定して使う。DHCP は実装していない)
- この実装以外の実装との相互接続
- 基板の乱数の統計的な質
- 自作の X25519(`c/src/oldp_x25519.c`)の処理時間が、秘密の値によって変わらないかどうか
- 暗号の部分の第三者による評価
- UART の線に実際に割り込む相手に対する基板の動作(暗号で確かめられないフレームを捨てる決まりは、C と JavaScript のテストで確かめた)
